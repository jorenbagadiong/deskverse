# Database architecture (DV-004A)

Deskverse stores future **Affiliate Tickets** in a local PostgreSQL database
on your own computer. DV-004A sets up only the foundation: installation,
configuration, migrations, a health check, tests and backups. It doesn't add
any ticket tables or pages yet; those come in DV-004B.

**PostgreSQL isn't needed for Pixel Studio or the office.** They work exactly
as before with the database stopped, missing or misconfigured. Pixel Studio's
render jobs stay as files on disk (see [Pixel Studio compatibility](#9-pixel-studio-compatibility)).

## 1. Overview

| Part       | Choice                                                                   |
| ---------- | ------------------------------------------------------------------------ |
| Server     | PostgreSQL 16 from Ubuntu 24.04's own repository (`apt`)                 |
| Network    | Listens on `127.0.0.1:5432` only                                         |
| Auth       | Password (`scram-sha-256`), two dedicated non-superuser roles            |
| Driver     | `pg` (node-postgres), bounded pool                                       |
| ORM        | Drizzle ORM (`drizzle-orm/node-postgres`)                                |
| Migrations | Versioned SQL in `drizzle/`, generated by `drizzle-kit`, applied by Yarn |
| Secrets    | `.env.local` (mode 600, Git-ignored); `.env.example` holds placeholders  |
| Health     | `GET /api/system/database/health` + "Local PostgreSQL" card on `/`       |
| Backups    | Offline: `pg_dump` + Pixel job files + checksummed manifest              |

| Role             | Database         | Used by                             | Privileges                                    |
| ---------------- | ---------------- | ----------------------------------- | --------------------------------------------- |
| `deskverse_app`  | `deskverse`      | the app, `yarn db:migrate`, backups | owns its database; not superuser              |
| `deskverse_test` | `deskverse_test` | `yarn test:db`, the E2E server      | owns its database; `CREATEDB` for scratch DBs |

Each database only accepts its own role (`CONNECT` is revoked from
`PUBLIC`), so the test role can't reach development data, and vice versa.

## 2. Installing PostgreSQL (WSL2 Ubuntu)

WSL must have systemd enabled (`/etc/wsl.conf` → `[boot] systemd=true`).
Then, from the repository root, as your normal user:

```bash
bash scripts/db/setup-local.sh
```

The script asks for your sudo password in your own terminal. It never reads,
prints or stores it. It is safe to run again and never drops anything. It:

1. Installs `postgresql` and `postgresql-client` from Ubuntu's repository.
   No third-party repository is added.
2. Writes one drop-in file,
   `/etc/postgresql/16/main/conf.d/deskverse.conf`, containing
   `listen_addresses = '127.0.0.1'`. That is the only server setting changed.
   `pg_hba.conf` is not edited: Ubuntu's default already requires
   `scram-sha-256` for `127.0.0.1`. The script checks this and stops if it
   isn't so.
3. Enables and starts the `postgresql` service, so it starts with WSL.
4. Creates both roles and databases, and revokes cross-access.
5. Generates random 48-character passwords and writes them to `.env.local`
   (mode 600). They go to `psql` through stdin, never on a command line.
   Existing entries in `.env.local` are kept. If a role exists but its entry
   is missing, it gets a new password.

Then:

```bash
yarn db:migrate   # apply the schema
yarn db:check     # confirm Deskverse can connect
```

### Managing the service

| Task                    | Command                                                            |
| ----------------------- | ------------------------------------------------------------------ |
| Status                  | `systemctl status postgresql` or `pg_lsclusters`                   |
| Start / stop / restart  | `sudo systemctl start\|stop\|restart postgresql`                   |
| Is it accepting?        | `pg_isready -h 127.0.0.1 -p 5432`                                  |
| Which addresses?        | `ss -ltn 'sport = :5432'` (expect only `127.0.0.1:5432`)           |
| Server log              | `sudo journalctl -u postgresql@16-main` and `/var/log/postgresql/` |
| Deskverse's view        | `yarn db:check`                                                    |
| Admin shell (superuser) | `sudo -u postgres psql`                                            |

After `wsl --shutdown` (or a Windows restart), the service starts again
automatically the next time WSL starts.

## 3. Configuration

`.env.local` (created by the setup script; template: `.env.example`):

```dotenv
DATABASE_URL=postgresql://deskverse_app:REPLACE_ME@127.0.0.1:5432/deskverse
DATABASE_TEST_URL=postgresql://deskverse_test:REPLACE_ME@127.0.0.1:5432/deskverse_test
```

Rules, enforced by `src/server/db/config.ts`:

- The scheme must be `postgresql://` (or `postgres://`).
- The host must be loopback: `127.0.0.1`, `::1` or `localhost`. Deskverse
  refuses to connect to another machine.
- A user, a password and a database are required, and `REPLACE_ME` is
  refused.
- No `?options` or `#fragment`. A query string could redirect `host`, switch
  TLS or point at a socket. The parsed fields are passed to `pg` separately,
  never as a connection string.
- Error messages name the variable, never its value, user or password.

How each process gets these values:

| Process                            | How it gets the values                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| `yarn dev` / `yarn start`          | Next.js loads `.env.local` itself                                             |
| `yarn db:*` scripts                | `scripts/load-env.ts` loads `.env*` the way `next dev` does (`@next/env`)     |
| `yarn test:db`                     | `tests/db/helpers.ts` reads only `DATABASE_TEST_URL`; DATABASE_URL is deleted |
| Playwright's own server            | gets the test URL as `DATABASE_URL` (see §7)                                  |
| Future background worker (DV-004C) | must import `scripts/load-env.ts` (or equivalent) first                       |

Nothing connects at import time or during `next build`. The app's pool is
created on first use (`getDatabase()`), and the health route is dynamic.

## 4. Code layout

```
src/server/db/
  config.ts       DATABASE_URL parsing and validation (pure)
  errors.ts       driver error → fixed, safe message
  pool.ts         bounded pg.Pool + Drizzle instance (no server-only marker: scripts use it)
  client.ts       server-only lazy singleton for the app: getDatabase()
  schema.ts       Drizzle schema (DV-004A: app_metadata only)
  migrations.ts   runMigrations() with an advisory lock, migrationStatus()
  journal.ts      the checkout's migration list (bundled JSON)
  health.ts       checkDatabaseHealth()
  test-guard.ts   test-database guards and scratch names
  env-file.ts     reads one .env file without touching process.env
src/server/backup/
  backup.ts       createBackup(), verifyBackup(), restoreBackup()
  manifest.ts     manifest format and validation
src/lib/system/database-health.ts      health report contract (client-safe)
src/app/api/system/database/health/    the endpoint
src/components/system/database-status.tsx   the "Local PostgreSQL" card
scripts/db/       yarn db:* command-line entry points, setup-local.sh
scripts/load-env.ts, server-only-hook.mjs   standalone-script support
drizzle/          versioned SQL migrations + drizzle-kit metadata (committed)
drizzle.config.ts drizzle-kit configuration (no credentials)
```

Pool limits (`pool.ts`):

- At most 5 connections.
- 3 s to connect, 10 s per statement (`statement_timeout`), and a client-side
  `query_timeout` slightly longer.
- Idle connections close after 10 s.
- An `error` handler is attached so a dropped idle connection (e.g.
  PostgreSQL restarting) is logged without the password and never crashes
  the Next.js server.

Scripts run with `tsx --import ./scripts/server-only-hook.mjs`. The hook
resolves the `server-only` marker to an empty module so scripts can reuse
server code (for example Pixel's `resolveDataRoot`). The Next.js app never
loads it.

There is no generic repository layer. Query code will live next to the
features that need it, starting with DV-004B.

## 5. Migrations

| Command            | What it does                                                           |
| ------------------ | ---------------------------------------------------------------------- |
| `yarn db:generate` | Turns schema.ts changes into a new SQL file in `drizzle/` (no DB)      |
| `yarn db:migrate`  | Applies pending migrations to `DATABASE_URL`; safe to repeat           |
| `yarn db:check`    | Read-only status: connection, schema state, server version, setup time |

How it works:

- Migration files are reviewed and committed. Drizzle records applied ones in
  `drizzle.__drizzle_migrations`.
- All pending migrations run in **one transaction**. If any statement fails,
  everything rolls back and the schema is exactly as before. The message
  includes PostgreSQL's reason, e.g. `relation "x" does not exist`; it never
  contains credentials.
- A PostgreSQL advisory lock serialises concurrent `db:migrate` runs.
- If the database has migrations the checkout doesn't know (it was migrated
  by newer code), `db:migrate` refuses and health reports `schema: "ahead"`.
- `drizzle-kit push` is deliberately not used: it would change a live schema
  without a migration file.
- Migrations may contain hand-added SQL. `0000_init.sql` seeds one
  `app_metadata` row, `database.initialized`, which is used to check that
  data survives restarts, backups and restores.

DV-004A schema: one table, `app_metadata (key text PK, value jsonb,
created_at, updated_at)`. There are no Affiliate Ticket, product, task,
approval or scheduling tables.

## 6. Health check

`GET /api/system/database/health`. It is read-only, takes no input, and is
sent with `Cache-Control: no-store`. It has the same loopback
Host/Origin/Fetch-Metadata guard as Pixel Studio, and is disabled on hosting
platforms.

```json
{
  "status": "ready",
  "message": "Local PostgreSQL is running and the schema is up to date.",
  "schema": "current",
  "checkedAt": "2026-11-21T10:00:00.000Z"
}
```

| `status`       | Meaning                                                                        | Card shows           |
| -------------- | ------------------------------------------------------------------------------ | -------------------- |
| `ready`        | Connected; `schema` is `current`, `pending` or `ahead`                         | Ready                |
| `unconfigured` | `DATABASE_URL` missing or invalid                                              | Not configured       |
| `offline`      | Nothing listening, starting/stopping, or no answer in time                     | Database not running |
| `error`        | Reached PostgreSQL but refused (password, missing DB, permissions, unexpected) | Connection failed    |

Each check:

- Opens one connection with `default_transaction_read_only=on`, runs
  `SELECT 1`, reads the migration table, then closes the connection.
- Is bounded at about 2.5 s overall.
- Returns only one of a fixed set of messages. It never includes the
  connection string, host, port, user or database name, paths, SQL or stack
  traces.

Unexpected errors are logged on the server, redacted.

## 7. Tests and test-database safeguards

| Command         | Needs PostgreSQL | What                                                                                                        |
| --------------- | ---------------- | ----------------------------------------------------------------------------------------------------------- |
| `yarn test`     | no               | config, URL validation, guards, error mapping, health with fake sockets, route guard, manifest, backup plan |
| `yarn test:db`  | yes              | connection, migrations, persistence, rollback, pool cleanup, timeouts, backup + isolated restore            |
| `yarn test:e2e` | optional         | "Local PostgreSQL" card states (mocked) + the real endpoint (read-only)                                     |

Safeguards:

- **Tests never use `DATABASE_URL`.** `tests/db/helpers.ts` reads
  `DATABASE_TEST_URL` (from the environment, else `.env.local`), keeps
  `DATABASE_URL` only to compare against, and deletes both from
  `process.env` before any test runs.
- **Guarded targets** (`assertTestDatabase`):
  - the database must be `deskverse_test` or `deskverse_test_*`;
  - the user name must contain `test`;
  - neither may match `DATABASE_URL`'s database or role.
- **Scratch databases.** Each test file creates its own
  `deskverse_test_<label>_<pid>_<random>` database and drops it afterwards.
  The drop helper refuses any name that isn't a scratch name, and the base
  `deskverse_test` database is never dropped. Parallel files can't collide,
  and every run starts from an empty database.
- **Role isolation is tested:** the test role is refused by the development
  database (`42501`).
- **Missing configuration fails the run.** Without `DATABASE_TEST_URL`,
  `yarn test:db` fails ("The database tests were NOT run"). It never skips
  and passes.
- **Isolated media.** Backup tests use temporary folders, never
  `~/.local/share/deskverse`.
- **E2E.**
  - The server Playwright starts gets `DATABASE_URL=<DATABASE_TEST_URL>`, or
    an empty value. An existing variable, even an empty one, stops Next.js
    loading `.env.local`'s `DATABASE_URL`, so it never sees your
    development database.
  - A reused server (`reuseExistingServer`) or `E2E_BASE_URL` may be using
    any database. DV-004A's E2E tests are read-only, so this is safe.
  - Future tests that write to the database must run with `E2E_DATABASE=1`.
    That starts a fresh server on port 3211, never reuses one, and refuses
    `E2E_BASE_URL`.

## 8. Backup and restore

A database dump and a file copy aren't one atomic snapshot, so **backups are
offline only**.

### Taking a backup

1. Stop Deskverse: `yarn dev`/`yarn start`, any running render, and (later)
   the worker.
2. Run `yarn db:backup` (default folder `~/.local/share/deskverse-backups/`,
   or `--out <folder>`). It refuses while:
   - a Deskverse Next.js server is running from this repository;
   - any process is working inside the data folder (e.g. FFmpeg);
   - anything else is connected to the database;
   - the schema isn't current.
3. Copy the new `deskverse-backup-<UTC time>/` folder to another drive.
4. Start Deskverse again.

What a backup contains (folder mode 700, files 600):

```
deskverse-backup-20261121T123456Z/
  manifest.json      contents, SHA-256 of every file, schema version, row counts
  manifest.sha256    checksum of manifest.json
  database.dump      pg_dump custom format, --no-owner --no-privileges
  media/video/jobs/<jobId>/job.json, project.json, assets/…, output/video.mp4
```

What is left out:

- Each job's `work/` folder (temporary render files).
- Symlinks and anything that isn't a recognised job file.
- Role passwords: `pg_dump` doesn't dump roles, and `pg_dump` /
  `pg_restore` get the password through `PGPASSWORD` in a minimal child
  environment, never on a command line. The manifest holds no user names,
  connection strings or absolute paths.

How a backup is written: it goes to `<name>.partial`, then is verified (every
checksum, and `pg_restore --list` must read the dump), then renamed. A failed
backup leaves nothing behind.

```bash
yarn db:backup:verify ~/.local/share/deskverse-backups/deskverse-backup-…   # re-check later
```

### Restoring

```bash
yarn db:restore <backup folder> --target DATABASE_URL --data-dir <new empty folder>
```

Restore never overwrites anything. It verifies the backup first, then
requires:

- an **empty** target database (no user objects);
- a target data folder that doesn't exist or is empty.

It then:

1. Restores the database in a single transaction (`pg_restore
--single-transaction --exit-on-error`).
2. Copies the media files and re-checks every checksum.
3. Confirms that the schema version and every table's row count match the
   manifest.

To switch to restored data, point `DATABASE_URL` at the restored database
and `DESKVERSE_DATA_DIR` at the restored folder.

On a fresh machine:

1. Run `setup-local.sh`. It creates an empty `deskverse` database; leave out
   `yarn db:migrate`.
2. Run `yarn db:restore … --target DATABASE_URL --data-dir
~/.local/share/deskverse`. The data folder must not exist yet.

Compatibility:

- `pg_restore` must be the same major version as the dump or newer; the
  manifest records both the server and `pg_dump` versions.
- The backup format is versioned (`formatVersion: 1`), and the restore
  refuses versions it doesn't know.

**Tested** (`tests/db/backup.db.test.ts`). A fixture is backed up from a
scratch database and a temporary data folder that holds a real Pixel job
created by Pixel's own storage code. It is restored into a second scratch
database and a new temporary folder. Records are read back through Drizzle
and the job through Pixel's storage API. The tests also cover damage
detection, refusal to restore over non-empty targets, and refusal while
another connection is open.

## 9. Pixel Studio compatibility

- Pixel Studio's data stays where and how it was: files under
  `~/.local/share/deskverse/video/jobs`. DV-004A doesn't move, rename,
  rewrite, migrate, delete or reformat anything there. No Pixel code reads
  the database.
- Rendering, uploads, history, retry, cancellation, deletion, restart
  recovery and the FFmpeg queue are unchanged. Verified at DV-004A:
  - with PostgreSQL running: unit, FFmpeg integration and the full E2E suite
    (24 known office/WebGL failures only);
  - with PostgreSQL stopped (`systemctl stop`): 42 Pixel, page and
    database-status E2E tests passed against a production build, including
    real FFmpeg renders, cancellation and history. Health reported
    `offline`, and the server stayed up.
- Backups read Pixel's files without changing them. Restores only write into
  a new, empty folder.
- PostgreSQL becomes the source of truth for **Affiliate Tickets**. Linking
  tickets to render jobs is planned for DV-005C.

## 10. Security

- **Network:** listens on `127.0.0.1` only, and URLs pointing at any other
  host are rejected in code. `ss -ltn` shows only `127.0.0.1:5432`.
- **Authentication:** `scram-sha-256` passwords. The app and test roles are
  not superusers and can't create roles. The test role's `CREATEDB` is the
  only extra privilege, needed for scratch databases.
- **Secrets:**
  - They live only in `.env.local` (mode 600, Git-ignored). `.env.example`
    holds `REPLACE_ME` placeholders.
  - There are no `NEXT_PUBLIC_` database variables, and the database
    modules are server-side.
  - Passwords are redacted from logs, and URLs never appear in messages or
    responses.
- **Queries:** values are parameterised. The few identifiers (table names
  in backups, scratch database names) are quoted with `escapeIdentifier`,
  and scratch names are also pattern-checked. The browser can't send SQL;
  the health endpoint takes no input.
- **Bounded:** pool size, connect, statement and health timeouts.
- **Non-destructive defaults:** `db:migrate` only moves forward,
  transactionally. `db:backup` only reads. `db:restore` only writes into
  empty targets. Tests only drop guarded scratch databases.
- The localhost guard is not authentication. The real boundary is that
  PostgreSQL and the Next.js server (`-H 127.0.0.1`) listen on loopback.
  DV-004A adds no users or logins.

## 11. Common connection problems

| Symptom (card / `yarn db:check`)                | Likely cause → fix                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Not configured: `DATABASE_URL isn't set`        | No `.env.local` → run `scripts/db/setup-local.sh`                                                |
| Not configured: `… still has the REPLACE_ME …`  | Copied `.env.example` without passwords → run the setup script                                   |
| Not configured: `… must point at this computer` | URL host isn't 127.0.0.1 → fix the URL (remote databases aren't supported)                       |
| Database not running                            | Service stopped → `sudo systemctl start postgresql`; check `pg_lsclusters`                       |
| Database not running right after WSL starts     | Still starting → wait a few seconds; check systemd is enabled in `/etc/wsl.conf`                 |
| Connection failed: `refused the password`       | `.env.local` and the role disagree → delete that line, rerun the setup script                    |
| Connection failed: `database doesn't exist yet` | Database dropped/not created → rerun the setup script                                            |
| Ready, but `schema needs updating`              | New migrations → `yarn db:migrate`                                                               |
| `yarn test:db`: `DATABASE_TEST_URL isn't set`   | Setup not run, or the line was removed → rerun the setup script                                  |
| Port 5432 in use by something else              | Another PostgreSQL (e.g. on Windows) → stop it, or change the cluster port and URLs deliberately |

## 12. Limitations and next milestone

- **Offline backups only.** There are no online snapshots or scheduled
  backups. Backups are as safe as the drive you copy them to.
- **Restore requires an empty database.** Merging or partial restore isn't
  supported.
- **Running-process detection is Linux-only** (`/proc`). On other systems
  `db:backup` refuses rather than guessing.
- **One local cluster.** PostgreSQL runs inside WSL, and Windows apps reach
  it only through WSL's localhost forwarding, which isn't needed or
  documented here.

and `/tickets/[ticketId]`, built on this foundation, with new versioned
